## Independent disposable-Redis QA evidence (November 22, 2026)

The follow-up security QA branch at `50bcfa54c5207066816759c98190e3c93212a7c9` passed [GitHub Actions run 45073521287](https://github.com/Atiyk/Stat-Window/actions/runs/45073521287): TypeScript, 29 Vitest files / 379 unit tests including actual disposable Redis 7 integration, API bundle parity, factory/content checks and application build. A strict TypeScript `HeadersInit` fixture error in the first run was fixed on the isolated QA branch. The code remains UNVERIFIED against hosted Upstash REST strict-key locking and actual command billing; do not enable leaderboard until $0 spend, full erasure, and independent final privacy/security critic approval on exact integration SHA.


The opt-in leaderboard remains disabled by default. The worker fixes the shared command ceiling: all leaderboard reads and submissions atomically check the existing percentile budget counters (380,000 monthly and daily cap) and their own separate monthly suballocation (at most 20,000). Both are charged in the same Lua script. This is a suballocation **inside** the existing 380,000, not an extra 20,000. Existing percentile deletions continue to use their separate 20,000 reserve. Upstash Free's 500,000 monthly command quota includes operations outside these scripts; budget accounting and real Redis tests remain mandatory before activation.

Ranking seasons are fixed 120-day UTC blocks anchored to 2026-01-01, rather than the unbounded beta/s1 game season. Day/week/month/120-day-season boards expire 30 days after the end of their respective periods. The browser-linked hash expires at the latest of those four fixed deadlines; this prevents the hash expiring before a still-retained season board when another player refreshes the board. Scores are not verified against cheating; no prizes.

GET requests have atomic per-network limits of 12 per fixed UTC minute and 60 per UTC day; POST has 4 per fixed UTC minute and 20 per UTC day; DELETE has 2 per fixed UTC minute and 6 per UTC day, returning 429 with Retry-After. The minute counters have 120-second cleanup TTLs but the key rotates every minute. These counters are Redis operations and need vendor command-cost validation; they are not yet accounted in the existing estimate.

## Verification status and launch blockers (2026-11-22)

- Integration PR #23 at `c92983422955f7335c083728a5d2695f955b41a0` previously reported 372 Vitest passes, including 10 Redis 7 leaderboard tests (CI run 45055339467). **Those results are not a pass for this worker branch**; new code and tests have not executed in CI.
- **New deletion safety:** `erasureBoardKeys` enumerates the finite board universe for the current and previous 120-day blocks (one key per day plus deduplicated week, month and season keys). DELETE passes these names as explicit `EVAL KEYS[8+]`; Lua verifies every ledger reference against the declared list **before** reserving money or changing a score. Unexpected keys return `paused`, never a false deletion success. The atomic script uses exactly the declared keys when updating rankings. No database-wide `SCAN` or user-supplied key names.
- Upstash documents that **Lua strict key locking can reject undeclared keys**, whereas ordinary scripts without the strict setting use its global lock (https://upstash.com/docs/redis/features/key-locking). The explicit-key change aligns with that documented rule, but **no actual Upstash REST + strict-locking test has been performed**. Test on isolated free-tier data with existing authorized configuration only, never on production participant records.
- Upstash bills one command for `EVAL` **plus one for each nested** `redis.call`/`redis.pcall` (https://upstash.com/docs/redis/overall/billing). The present 24/55 read/submit budget weights and 21 + 3*B (distinct boards) deletion weight are conservative upper bounds based on source inspection for successful script paths, **not measured provider accounting**, and failed/limited calls still incur commands. An attacker can repeatedly invoke capped requests; Redis-side counters alone cannot guarantee the 500K vendor quota. Verify billed usage, traffic forecasts, reserved percentile/erasure headroom and free-tier account status before enabling.
- Real deletion must also be tested with a ledger containing an out-of-range board, an expired daily board, a multi-block retained participant, and a fully consumed erasure budget. The deletion endpoint must return an error, not success, whenever records remain.
- Production client-IP/header provenance and real Vercel request handling remain to be verified; `X-Real-IP` is documented by Vercel as equivalent to edge-overwritten `X-Forwarded-For` (https://vercel.com/docs/headers/request-headers). The unknown-address fallback is intentionally shared, which may limit legitimate users.
- Independent security/privacy/cost critic approval on the **exact final integrated SHA** is still required. Do **not** enable `LEADERBOARDS_ENABLED` merely because the local Redis tests pass.

Redis 7 `EXPIREAT ... GT` prevents late submissions from shortening the owner hash's existing expiry. A disposable Redis integration suite now covers concurrency, deletion, budgets, read caps, monotonic expiration and POST daily caps; it must run with `REDIS_URL` against an isolated local/CI Redis 7 service before any release approval. Daily rate-limit counters themselves are not included in the vendor command cost proof. Keep feature disabled.

## Read-only personal rank and participation days (unverified implementation)

The leaderboard GET endpoint accepts an optional random 22-character browser code in the `X-Stat-Window-Player` request header; it never places the code into a URL, analytics or ranking payload. The backend hashes the code and uses a bounded per-player hash to compute the caller's own rank and number of accepted daily scores for the selected day/week/month/120-day season. Tied total scores share the same rank, and the public list uses the same tie convention. Client UI surfaces this only when someone has explicitly opted in. No personal rank is returned for a public anonymous GET. The response remains non-cacheable. Because this is a client-generated code without accounts, rankings are **unverified** and may be manipulated; do not award prizes.

The component suppresses the opt-in Join button while the backend is disabled or unavailable, avoiding the appearance that an offline ranking is live. Existing participant deletion remains available even if new submissions are disabled, subject to the separate deletion safeguards. This code change needs executable real Redis and browser CI plus security/cost critic approval before activation. 

## P0 block-ledger design (worker implementation, not yet independently verified)

Each participant's accepted dates are stored in a separate hash per fixed 120-day season (`player:<HMAC>:block-N`), rather than a single continuously renewed hash. Each hash expires at the latest expiry of any day/week/month/season board to which its 120 days can contribute. At most the current and preceding blocks are read or erased, with a hard 240-record limit. This accommodates a Monday week crossing a season boundary and the 30-day retention grace period. The legacy unpartitioned hash format was never approved for activation; if any environment has real legacy data, **do not enable this code** without a verified cleanup/migration.

Erasure uses two fixed ledger keys and an atomic Lua script. The ledger records contain derived board names. The current worker now explicitly declares the full bounded set of permitted board names in EVAL KEYS and fails closed when a ledger refers to a key outside this set. **Independent Upstash REST strict-locking compatibility and command-cost verification** remain required before activation. An erasure aggregates per-day contributions by distinct board and reserves `21 + 3*B` estimated commands (B = number of distinct referenced day/week/month/season boards, with at most 240 accepted dates). This reserves EVAL, fixed-rate/budget calls, and one ZSCORE plus at most one update per board. It is charged atomically to both the existing shared 20,000 monthly erasure reserve and a distinct leaderboard subcap (maximum 10,000, minimum 5,000 to enable). No-record deletion reserves 18 credits for a revocation marker, even if no record remains, and remains network-rate-limited. Two deletions per network per minute and six per day remain. A paused or limited erasure returns an error, never a success acknowledgment.

**Unverified:** The worker has added real Redis 7 regression scenarios, but has not executed Redis tests or vendor compatibility checks in this run. Keep the service disabled pending those gates and independent review.

## Erasure after consent withdrawal

DELETE requires the original random browser code but **does not require ongoing consent**. A participant may withdraw consent or enable GPC/DNT and still request removal; new POST submissions continue to require affirmative consent. Erasure remains accessible when leaderboard reads/writes are disabled, provided the store and secret are configured. An unavailable or paused Redis store must return an error, never falsely acknowledge deletion. Independent Upstash Lua dynamic-key compatibility and billing proof remain required.

## Erasure of already-expired boards (worker fix, pending CI)

Erasure now checks `ZSCORE` before subtracting a retained daily contribution. When an earlier daily board has expired, deletion skips that missing board rather than recreating it through `ZINCRBY` with a negative score. The Redis integration test explicitly removes the daily board before deleting the participant, then checks that the board remains absent and the other period entries are removed. This test has **not yet run on the new worker commit**. The derived-key Upstash strict-locking compatibility issue is **still unresolved**; do not activate the leaderboard based on this change alone.

Network throttling now ignores client-forgeable `X-Forwarded-For` and uses `X-Real-IP` when present, otherwise a conservative shared bucket. Verify the production edge guarantees that `X-Real-IP` is trusted before enabling. GPC and DNT explicitly reject new score submissions even when the body claims consent; erasure remains available after withdrawal.

## Explicit keys for atomic erasure

The delete store contract reserves `KEYS[1..6]` for the two player ledgers, monthly erasure reserve, short-window rate, daily rate and leaderboard erasure subcap. KEYS[7] is the HMAC-only 48-hour revocation marker; every potential day/week/month/season ranking key for those ledger blocks is passed through `KEYS[8..]`. The Lua script maps the declared names to their exact indexes, validates **all** ledger rows and only then performs budget charges and removal. It never uses a Redis key discovered during script execution unless that key is already declared, so default-global and strict-key locking paths share the same atomic semantics. This declaration-only change does not add nested `redis.call` commands; it increases the request key list size and lock fan-out, which require latency and vendor-compatibility measurement. The feature remains off pending those measurements.

## Consolidated per-board erasure (worker change, pending verification)

Rather than subtract the same player's daily score separately from a weekly, monthly, and season aggregate on every accepted day, DELETE first sums all retained ledger contributions for each unique declared board and then performs at most one sorted-set adjustment per board. This removes redundant Redis calls and should reduce script runtime and billed commands; the exact improvement must be measured on Upstash. Full 121-day, two-block erasure and counter-ceiling regressions have been added to the disposable Redis 7 suite but have **not run at this worker SHA**. A timeout or Lua error must not be claimed as a successful erasure.

## Denied-request Redis write bound (2026-11-22 worker patch; not yet tested)

All three leaderboard Lua endpoints now `GET` their per-network minute/daily counters and immediately return `limited` at the threshold, without another `INCR`. For permitted requests this adds one `GET` for each checked counter; for repeated 429s it avoids unbounded writes and prevents the rate counters from growing beyond 12/60 GET, 4/20 POST, or 2/6 DELETE. The new disposable Redis tests repeat 50 denied requests for each method and assert that the rate counters and paid-budget counters remain fixed. These are source/test changes, **not executed CI evidence**.

**Hard quota limitation:** even an early-rejected EVAL costs the EVAL itself and at least one nested `GET` (approximately two vendor commands per request); a sufficiently large unauthenticated flood can therefore still exceed the shared 500,000 monthly free quota despite the app-level budget counters. The percentile 380,000 command cap + separate 20,000 percentile erasure reserve + leaderboard's *included* 20,000 suballocation + separate 10,000 leaderboard erase subcap cannot prove a worst-case ceiling without trusted edge request limiting/quotas and measured vendor accounting. Leave the feature disabled until this is independently mitigated and tested. No paid tier is authorized.

## Warm-instance billable-denial guard (worker source change; isolated CI verified)

After a real Redis Lua request returns a rate-limit `limited` result (HTTP 429), the leaderboard handler now memoizes that denial only for the same HMACed network, endpoint method, Redis store instance and fixed UTC minute. Later identical attempts on that warm Vercel instance return HTTP 429 without calling Upstash again. A finite 512-entry cache prevents unbounded memory growth. New unit tests cover same-source repeated denials, separate network identities, minute rollover, DELETE separation and non-caching of 503/paused.

This is **defense in depth, not activation evidence**: function instances do not share memory and an attacker can rotate network sources or cause new instances. The first denied EVAL still incurs vendor commands; the pre-existing per-network Redis limiter remains authoritative. Do not enable `LEADERBOARDS_ENABLED` until hosted strict-key-locking, vendor-billed call measurements, operational/edge traffic caps and an independent security/cost PASS prove the shared $0 free-tier ceiling. No firewall setting or environment flag was changed by this patch.

## In-flight withdrawal race (security QA; pending complete vendor solution)

The client now waits for **same-tab** leaderboard POSTs that started before consent withdrawal to settle before it sends DELETE. It clears local consent before waiting, retains the deletion key after a failure and does not allow a late POST response to reassert UI enrollment. A browser regression deliberately holds a POST response, requests Leave and verifies POST completion occurs before DELETE.

**Mitigation staged, exact-SHA review pending:** the Redis DELETE/POST Lua pair now sets and checks a 48-hour HMAC-only revocation marker, including for an otherwise empty deletion, to stop cross-tab replays during the original day's submission window. No claim of hosted Upstash strict-lock/cost compatibility or independent privacy PASS is made.

## Atomic post-erasure revocation (new worker batch; exact CI pending)

A browser code that requested leaderboard deletion now receives a 48-hour HMAC-only Redis tombstone, created within the same atomic EVAL as score removal. The POST EVAL declares and checks that same key before any score mutation. This blocks a valid late submission from another tab or network invocation even if its original response arrives after erasure. An empty DELETE also reserves 18 Redis command credits and creates a tombstone, preventing DELETE-before-POST races; a nonempty erasure reserves `21 + 3 × distinctBoards`. Per-network request caps still apply. The tombstone contains no scores and expires after 48 hours; the application never reuses a revoked code. New isolated Redis 7 tests simulate both ordering races and verify no score/ledger resurrection.

**Do not enable** without passing exact-SHA CI, confirming all previously approved dollar-zero ceilings and independently verifying Upstash strict-locking and Lua billing. 48-hour protection covers late requests for a historical eligible day; a client that sends newly fabricated requests beyond the two-day window remains outside the browser's consent guarantee. A longer revocation marker remains a review question if the security critic requires it.
