# V5.2 measurement: what launch can and can't tell us

Source of truth for events: `src/lib/track.ts`; dictionary and reading guide: [MEASUREMENT.md](MEASUREMENT.md). Every event is a virtual page view on a fixed `/e/…` path in Vercel Web Analytics (Hobby). There are no cookies or player identifiers, so every number below is a count of paths, not a set of people. From Day 1 (2026-11-30) all paths carry the `/e/s1/…` prefix, so launch numbers never mix with beta.

## Measurable today

| Question | Path(s) | Measurable? | Limits |
|---|---|---|---|
| First visits | `/e/s1/visit/new` | Yes | Browsers, not people. Needs working localStorage; private windows and cleared storage look new every time. |
| Tutorial start / completion | `/e/s1/tutorial/{start,skip,complete}` | Yes, **added in V5.2** | `start` is per page load of the tutorial (a reload while it's open counts again); `skip` is "Skip tutorial and start" before the lock, `complete` is the Play button after the reveal. |
| Daily starts | `/e/s1/start/daily` | Yes | Once per browser and day (`trackOnce`). A friend's link for today counts as `start/challenge`, not daily. |
| Per-question abandonment | `/e/s1/lock/daily/r{n}/*`, `/e/s1/next/daily/r{n}`, `/e/s1/exit/daily/r{n}` | Yes | Drop-off at question n = `lock r(n-1)` minus `lock r(n)`. `exit` is best effort (browsers drop events on close) and only explains part of the gap. |
| Completions | `/e/s1/complete/daily/{band}` | Yes | Score bands of 100 only. |
| Share attempts | `/e/s1/share/{mode}/{native,clipboard,native-image,image-saved,failed,cancelled}` | Yes | An attempt, not a delivery: whether a message was sent or pasted is invisible. |
| Referral landings | `/e/s1/challenge-open/{today,past,future,invalid}[/with-score[/with-rounds]]` | Yes | Any visit with `?day=`, including the sender re-opening their own link. |
| Referred completions | `/e/s1/complete/challenge/{band}` | Yes | Same caveat: a sender replaying their own link counts. Can't be tied to the share that caused it. |
| Returning players | `/e/s1/visit/return/gap-{1,2-6,7plus}` | Yes | First open on a new Eastern day by a known browser. |
| D1 / D7 retention | `/e/s1/visit/return/…/day1` ÷ previous day's `visit/new`; `…/day7` ÷ `visit/new` seven days earlier | Approximate | Not a cohort: the numerator is "browsers whose first visit was exactly 1 (or 7) days ago and came back today", the denominator is that day's new browsers. Exact only if storage survives; no split by acquisition source. |
| Mobile vs desktop | Vercel dashboard's device panel, filtered to a path | Probably | No device segment is in our paths (deliberately). Confirm on Day 1 that the Hobby dashboard filters the device panel by page; if it doesn't, mobile vs desktop is only available for total page views. |

## What can't be measured without identifiers

- **Cohort funnels.** We can't follow one browser from tutorial to completion to next-day return. Ratios of path counts (e.g. `complete/daily` ÷ `start/daily`) are aggregate conversion, which is fine for big effects and misleading when the mix of new and returning players shifts.
- **Retention by source.** Whether referred players return more than organic ones: `visit/return` carries no source.
- **Share → referral attribution.** A referral landing can't be matched to the share that produced it, so "referred completions per share" is a ratio of daily totals, not a per-share rate.
- **People across devices.** Phone plus laptop is two browsers.
- **Players who block analytics.** Ad blockers, GPC/DNT and the in-app switch send nothing; this is a growing, non-random slice.

These are intentional (docs/PRIVACY.md). Closing them would need a per-browser identifier, which V5.2 rules out.

## Post-launch experiments

Not built. Each needs a per-browser arm stored in localStorage and an arm segment in the path, following the only existing pattern (`/e/x/survival-cta/{arm}/{step}`, readout in `scripts/analytics-readout.ts` with a 200-per-arm floor). Every arm gets the same five questions; only presentation changes. Run one at a time so their effects don't mix.

Sample sizes use n ≈ 16·p(1−p)/δ² per arm (80% power, two-sided 5%) with the baseline guesses shown; replace them with the first two weeks of real `s1` counts before starting.

### 1. Onboarding activation

- **Change:** the first-visit home and tutorial presentation (e.g. tutorial offered by default vs one tap away). Arm assigned at first visit.
- **Primary metric:** first-visit browsers that finish their first daily: `/e/x/onboarding/{arm}/complete` ÷ `/e/x/onboarding/{arm}/exposed` (exposed = first visit).
- **Secondary:** tutorial complete ÷ start; first-touch ÷ start.
- **Guardrails:** next-day return per arm (must not drop by more than 3 points); no axe failures on the changed screens; time-to-first-question not slower; returning players never see the experiment.
- **Minimum sample:** baseline 50%, detect +10 points: about **400 first-visit browsers per arm**.
- **Duration:** at least 14 days (two full weekly cycles), longer until both arms pass 400.

### 2. Challenge copy → referred completions

- **Change:** the share invitation line and the recipient gate wording (e.g. V5.2's "Think you know ball? Beat N." vs a plainer line). Arm per *sender* browser; the link carries no arm, so the recipient's landing copy must be the same in both arms or the arm must ride in a fixed-vocabulary link parameter.
- **Primary metric:** referred completions per share attempt: `complete/challenge/*` ÷ `share/daily/{native,clipboard}`, per sender arm. With no identifiers this is only attributable if the arm travels in the link (one extra bounded parameter, e.g. `&c=a|b`); without it, only share-attempt rate per completion is attributable.
- **Guardrails:** share text stays spoiler-free (unit test in `src/engine/summary.test.ts`); share attempts per completion must not fall; `challenge-open/invalid` must not rise.
- **Minimum sample:** baseline 10% referred completions per share, detect +5 points: about **600 share attempts per arm**.
- **Duration:** at least 14 days, and 2 more days after the last counted share for late opens.

### 3. Weekly progress visibility → retention

- **Change:** where the week-so-far appears (e.g. the Weekly glance on the results screen and home vs behind its link). Arm per browser at first visit.
- **Primary metric:** D7 return: `visit/return/…/day7` ÷ `visit/new` seven days earlier, per arm.
- **Secondary:** D1 return; `streak/daily/2-6` + `7plus` share of streak events; `weekly/open/*`.
- **Guardrails:** completion rate per start unchanged; no extra events beyond budget (check the Hobby cap of 50,000 a month); no new layout overflow at 320 px.
- **Minimum sample:** baseline 15%, detect +5 points: about **820 new browsers per arm**.
- **Duration:** enrolment for at least 14 days plus 7 days of follow-up, so 3 weeks minimum.

Traffic check before starting any of them: at about 17 events per complete game, the Hobby cap allows roughly 2,900 complete games a month. Experiment 3 alone needs about 1,640 new browsers, so it may take more than a month at launch traffic.
