# Stat Window V5.3 launch measurement

Use the [event dictionary](MEASUREMENT.md) for exact paths. Official events use `/e/s1/…`. Beta uses `/e/…` and QA uses `/e/qa/…`. Run start, diagnostics, completion, streak and result shares follow the puzzle’s season even if the browser stays open through Eastern midnight. The real page view `/` includes all three groups.

## First 30 days

| Readout | Count or calculation | Interpretation |
|---|---|---|
| New browsers | `visit/new` | A first visit with usable local storage. A person can use several browsers. |
| Daily starts and finishes | `start/daily`, sum `complete/daily/*` | Divide finishes by starts over the same multi-day period. The working hypothesis is at least 75%. Some runs finish after their start date. |
| Share actions | Sum `share/daily/*`, then divide by daily finishes | The working hypothesis is at least 10 recorded attempts per 100 finishes. One finisher can record several attempts. A share action is counted once it reports an outcome. |
| Share outcomes | `native`, `clipboard`, `native-image`, `image-saved`, `cancelled`, `failed` | Native share resolution, clipboard copy and local image save are observable. Message delivery, pastes and abandoned share sheets are unobserved. |
| Challenge arrivals and finishes | Valid `challenge-open/{today,past}` and sum `complete/challenge/*` | Absolute counts first. Re-opens can count again. The person who shared a link can also open it. No sender or recipient ID links the counts. |
| Repeat visits | Sum `visit/return/*` | Returning browsers who open the site on a later Eastern day. Streak buckets show consecutive daily finishes among browsers that finished an eligible daily. |
| D1 and D7 estimates | Return views ending in `/day1` or `/day7` on day t ÷ `visit/new` on t–1 or t–7 | Use day-aligned ranges and mature official-season dates. Storage loss, analytics opt-out, cross-device play and the provider’s reporting timezone can bias the ratios. |
| Question progression | `sample/start/daily`, `sample/first-touch/daily`, `sample/lock/daily/r1…r5` | Use the same sampled cohort at every step. Compare Q1 locks with sampled starts, then compare each lock count with the preceding lock count. Use hit and miss counts at the same position for hit rate. |
| Failures and quotas | Sum `failure/game` and `failure/comparison` separately. Review Vercel Usage and Upstash Commands. | A comparison can be unavailable because of network, storage or service capacity. A game label covers failed loading of a scheduled puzzle or an uncaught React error. Neither event sends error details. |

Start with daily counts. Review the funnel after the partial opening week, after the first full week, and on Days 14 and 30. Copy fixed-path **page view counts** from Vercel once a week. The Hobby reporting window is one month. Keep the recording window, timezone, source, possible lag, and any QA or collection gaps with each export. Leave unavailable values blank. Keep launch thresholds as hypotheses.

```bash
node --experimental-strip-types scripts/analytics-readout.ts pages.csv --cohort s1
```

For fewer than 30 observations at a denominator, record counts and defer rate conclusions. The diagnostic sample is about one in ten eligible browser-runs. It takes roughly 300 starters to expect 30 sampled starts, and more to measure later questions. Full-volume counts provide the launch headline. Sampled ratios remain directional where browsers block storage or providers lose events. Weekly reports should compare the same number of weekdays and preserve the short first week as its own period.

## Expected event volume

On a standard daily that starts and finishes on one page load, the core sequence is one real page view, one new or returning browser visit, one daily start, one daily completion and one streak bucket. Up to seven diagnostics on 10% of starts add up to 0.7 views per such journey on average. One recorded share action adds one. A tutorial adds its impression and, if performed, one action. A page reload adds a page view. A later return within the same Eastern day may have only the page view. Weekly, Survival and other deliberate actions add their own events when used.

The V5.2 budget assumed about 17 events for a completed game with one share. The comparable V5.3 estimate is at most 6.7 on average, about 61% lower. Treat those figures as journey models. Each additional site project, incomplete run, tutorial or repeated share also uses the team allowance.

## Free-tier planning model

Checked November 27, 2026. Vercel Hobby includes 50,000 analytics events per month across projects. Collection can pause at its ceiling. Hobby is limited to personal or noncommercial use. Review hosting eligibility before monetization, ads or sponsored commercial activity. [Vercel Web Analytics pricing](https://vercel.com/docs/analytics/limits-and-pricing) · [Vercel terms, Hobby Plan](https://vercel.com/legal/terms#4-hobby-plan).

Upstash Redis Free includes 500,000 commands per month, 250 MB data and 10 GB monthly bandwidth. A Lua script is charged for the evaluation plus each command it calls. A database at its request limit can reject commands. [Upstash billing](https://upstash.com/docs/redis/overall/billing) · [Upstash limit behavior](https://upstash.com/docs/redis/troubleshooting/max_requests_limit).

The model uses a 30-day month and 6.3 analytics views per daily starter, including an allowance for tutorials, reloads, referrals and visits without a start. Redis demand assumes 75% finish, 80% of finishers submit a valid score, 27 charged commands per full submission and 12 per origin cache miss. The read estimate is 5 origin misses per 100 starters, capped at the application’s approximate 333 daily reads. Actual reads depend on the edge cache and geography. Costs exclude retries, cleanup, unrelated database use and paused calls. Headroom starts from an unused provider allowance.

## Experiment briefs

Keep the first clean baseline before assigning a browser to a test. Use one active experiment and fixed-vocabulary arms. No individual analytics identifiers are required. Minimum samples are rough 80%-power targets per arm for a two-sided 5% test. Recalculate from launch traffic and account for repeat-browser clustering.

| Experiment | Primary measure | Guardrails | Planning sample |
|---|---|---|---|
| Optional versus more prominent onboarding | First-visit daily finish per first-visit exposure, by arm | Q1 starts, time to first question, D1 return, accessibility and no change to returning-player experience | 400 eligible first visits per arm for 50% baseline and +10 points. Cover two full weeks. |
| Friend-challenge invitation copy | Link handoffs or copies per completed sender run, by arm | Recorded cancellation, malformed links, no spoilers or unusual referral loss | About 600 completed sender runs per arm for 10% baseline and +5 points. Referred finishes by sender arm require a separate bounded link tag and independent privacy review. |
| Weekly progress visibility | D7 return per eligible first-visit exposure, by arm | Daily completion, 320 px layout, initial time to play and event cap | About 820 new browsers per arm for 15% baseline and +5 points. Enroll for two full weeks and allow seven more days for follow-up. |
